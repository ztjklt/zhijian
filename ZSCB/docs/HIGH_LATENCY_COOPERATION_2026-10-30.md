# 600ms 协作修正与合并门槛

2026-10-30，维持SPEC v0.55、r22／协议11。用户明确要求修好600ms协作，验证与CI均通过后合并GitHub主分支；本任务不发布Railway／Maker，不修改真实存档或凭据。

## 复现与根因

原失败为跨作者固定连接未出现。加入时序取证后，600ms并非每次失败：第2、3、5次通过，第4次在相同600ms／每向256KiB/s条件下再次失败。失败时，朋友已收到撤销搬动回执，房主仍在重同步：`ready=false`，两次点击的序号均为`90→90`，没有发送连接命令，也没有服务器连接回执。界面却显示“正在等待服务器确认连接…”。

两个问题共同造成误判与操作丢失：

- `send_op`在未Ready时返回-1并说明正在同步，但`connection_action`无条件覆盖提示为等待确认；第二锚点操作还会清掉尚未提交的第一锚点。
- 共建机器人在另一端撤销后固定等0.6秒，误把墙钟时间当成房主已经完成重同步。

首次诊断代码曾引用错误的`game.status_text`，修正为`toolbar.status_text`；该夹具错误日志保留，不当成游戏错误。取证不包含真实用户身份／作品。

## 修正

连接提交返回是否真正被接收。发送被拒绝时保留原同步提示与未提交锚点；Ready恢复本身不自动重发，玩家再次点击才发送一次连接。离线连接原有选点生命周期保持。权威权限、材料接缝、距离、版本、物理与保存格式不变。

机器人不再用固定等待：核对被撤销部件的稳定ID、move＋undo后的版本、Ready／非同步状态，以及实际复制刚体已收敛到服务器目标后才继续连接。跨进程撤销收据先完整写临时文件，再原子改名，避免看到半份JSON。仍需真正的连接回执、双方共享结构、撤权拒绝、保存和重开；不延长原超时或放宽断言。

## 验证与CI

- 新增真实锚点／实际发送接口回归先RED8项／5失败，修正后通过；加入旧Ready／旧版本／未收敛复制体测试后13／0。
- 既有结构UI、结构网络、协作权威／复制回归5／5通过。
- 原生＋匹配Web各两个完整客户端，临时本机权威，600ms额外RTT、每向256KiB/s：绘画、开放借用、搬动撤销、跨作者连接、撤回拒绝、保存与重开通过。
- 独立只读复核未发现新增P0／P1／P2，未放宽既有权限、连接或保存断言。

完整验证命令（全部在随机私有目录）：

```sh
python3 ZSCB/tests/run_checks.py --stages native python web cooperation --logs /tmp/zhijian-600-final
```

只重跑高延迟双客户端：

```sh
python3 ZSCB/tests/run_checks.py --stages cooperation --logs /tmp/zhijian-600-cooperation
```

GitHub CI使用固定Godot4.6.3 Linux，先执行原生／Python／当前Web完整行为，再执行相同600ms原生与Web双客户端。分支通过PR触发，主分支通过push触发；旧提交运行可取消，同一提交不重复执行push和PR两份。CI与合并状态以[PR #1检查页](https://github.com/ztjklt/zhijian/pull/1/checks)为准；只在本地验证及当前提交CI通过后合并，不以旧提交的绿色结果代替。

## 范围

修正了已复现的同步阶段连接反馈与测试时序，不把一次或有限次受控通过称作所有高延迟操作都流畅。Web适配GDScript双客户端不等于浏览器WASM；异地两台物理设备及当前公网更新仍不属于本次验收。原始失败记录继续保留，凭据／存档／原始证据不入GitHub。
